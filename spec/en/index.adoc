= FPSOT style specification
include::_fpsot-terms.adoc[]

This specification sets the visual look of the screens of {abbr-fpsot-first} products.
It covers design tokens, the behavior of components and the themes that give a product its look.
A design token is a named value, such as a color or a space.
A component uses the token instead of a raw value.
A theme gives a value to each token.
One product can then look like link:https://www.patternfly.org/foundations-and-styles/design-tokens/overview[PatternFly], or like the sites of the governments of Québec and Canada.

The rules come in seven parts.

* xref:tokens.adoc[Design tokens] set the token format, the token tiers and token names.
* xref:categories.adoc[Token categories] cover color, type, spacing, radius, elevation, motion and layout.
* xref:states.adoc[Component states] cover focus, hover, the pressed state and the disabled state.
* xref:feedback.adoc[Errors, loading and empty states] cover how a screen reports errors, waits and empty views.
* xref:destructive.adoc[Destructive actions] cover undo, and how a person confirms an action that cannot be undone.
* xref:themes.adoc[Themes] set what a theme may contain, and the default, Québec and Canada themes.
* xref:theme-check.adoc[Checking a theme] sets how to check each theme against the accessibility rules.

The {abbr-fpsot} accessibility specification owns every accessibility rule, such as contrast, focus visibility and motion.
This specification points to it and never restates or changes one of its values.
The {abbr-fpsot} writing specification sets the wording of labels and messages.
The {abbr-fpsot} naming specification sets the rules for names that machines read, token names included.

The engine of {abbr-fpsot} screens is link:https://sitenetsoft.org/quarkus-pha/[quarkus-pha], which combines PatternFly, HTMX, Alpine.js and Qute templates.
This specification uses it as its reference implementation.
This mention is informative: a product conforms with any engine that meets the rules.

== Conformance

[quote, 'link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]']
____
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 (link:https://www.rfc-editor.org/info/rfc2119[RFC 2119], link:https://www.rfc-editor.org/info/rfc8174[RFC 8174]) when, and only when, they appear in all capitals, as shown here.
____

The keywords follow requirement WRT-010 of the {abbr-fpsot} writing specification.
The French version uses the French keywords of WRT-011.

This specification has two conformance classes.
A product conforms when its screens meet every MUST rule on tokens, components and destructive actions.
A theme conforms when it meets every MUST rule on themes and on checking a theme.
A product that uses a theme still needs its own accessibility check.
